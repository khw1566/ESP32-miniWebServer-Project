# S3 / C3 판매 제품 보안 개선 계획

## 범위와 현재 상태

이 문서는 현재 소스를 점검한 뒤 작성한 구현 계획입니다. 화이트리스트 및 아래 보안 조치는 아직 펌웨어에 적용하지 않았습니다. S3와 C3에 동일한 정책을 적용하되 C3의 메모리·파티션 한도를 고려합니다.

일반 콘텐츠 방문자는 그대로 웹페이지를 열 수 있게 하고, 관리자 기능에 화이트리스트를 우선 적용합니다. 비공개 콘텐츠 제품에는 방문자 인증을 별도 옵션으로 제공합니다.

## 소스에서 확인한 우선 위험

| 위험 | 확인 위치 | 우선 조치 |
|---|---|---|
| 파일 업로드·삭제·OTA에 관리자 인증 없음 | main/web_server.c의 api_upload_post_handler, api_delete_post_handler, api_ota_post_handler | 서버의 공통 인증 검사 필수 |
| 시스템·로그·파일 목록 조회 및 Wi-Fi 재설정에 일관된 접근 제한 없음 | 같은 파일의 API 및 setup/wifi 처리 | 역할별 허용 목록 적용 |
| 기본 관리자 비밀번호 0000 및 웹 저장소 복원 시 0000으로 되돌림 | 설정 처리 | 제품별 초기 비밀값과 최초 관리자 설정 도입; 콘텐츠 초기화와 인증 초기화 분리 |
| Wi-Fi 설정 페이지에 저장된 비밀번호를 JavaScript로 전달 | render_setup_page의 savedDefaultPass | 기존 암호는 반환하지 않고 서버 안에서 재사용 |
| 관리자 비밀번호를 브라우저 sessionStorage에 보관하고 반복 전달 | web_page_admin.c와 web_page_ai.c | 만료되는 세션과 별도 등록 브라우저 토큰 사용 |
| 웹파일과 관리자 기능이 같은 웹 출처에서 실행됨 | 정적 파일·관리자·AI 페이지 | 관리용 출처 분리; 사용자 HTML이 관리 API를 사용하지 못하도록 설계 |
| 암호화되지 않은 HTTP | 현재 HTTP 서버 | 신뢰 가능한 TLS 및 인증서 공급 방법을 판매 전에 확정 |
| Secure Boot, Flash Encryption, NVS Encryption 비활성화 | 두 sdkconfig | 개발 기기에서 검증 후 생산 프로필 도입 |

HTML 내 SSID·JSON 문자열 등 외부 입력의 출력 이스케이프, 파일명 URL 디코딩·경로 정규화도 함께 검토합니다. 이 점검은 소스 검토이며 침투 시험 결과는 아닙니다.

## 화이트리스트 설계

### 기본: 등록된 관리자 브라우저

IP 또는 MAC 주소를 관리자 신원으로 사용하지 않습니다. DHCP·IPv6 주소는 바뀌고, 공유기를 경유하는 HTTP 서버는 고객 휴대전화의 실제 MAC을 신뢰해서 확인할 수 없습니다. IP 허용 목록은 별도 제한 계층으로만 사용합니다.

- 공장 eFuse MAC/제품 시리얼/mDNS 주소는 공개 식별자이며 초기 비밀번호나 등록 비밀키로 사용하지 않습니다.
- 제품마다 별도로 생성한 무작위 초기 등록 코드를 라벨 또는 동봉 카드에 제공합니다. 비밀 코드는 공개 웹 접속 QR에 포함하지 않습니다.
- 소유자는 초기 등록 코드로 첫 관리자를 만들고 관리자 비밀번호를 설정합니다. 공통 기본 비밀번호와 무인 첫 접속 자동 등록은 없앱니다.
- 등록 브라우저는 암호학적으로 안전한 256비트 무작위 토큰으로 식별합니다. 보드에는 토큰의 검증값과 별칭을 저장합니다. 사용자 에이전트나 브라우저 지문은 인증 자료로 쓰지 않습니다.
- 등록된 브라우저에서도 관리자 로그인이 필요합니다. 관리자 세션은 유휴 15분, 최대 8시간 등 명시된 시간 후 만료하도록 설계합니다.
- 관리 화면의 승인 목록에는 별칭, 등록 시각, 최근 사용, 취소 기능을 제공합니다. 최대 8개부터 시작합니다.
- 새 기기 등록은 기존 관리자 승인 또는 유효한 초기/복구 코드와 재인증을 요구합니다. 장기 토큰은 URL·로그에 넣지 않습니다.
- 등록 취소 시 해당 브라우저의 장기 토큰과 세션을 함께 폐기합니다. 비밀번호 변경 시 세션 정책도 명시합니다.
- 저장 토큰은 실제 하드웨어 신원 증명이 아닙니다. 탈취된 토큰을 막으려면 TLS, 관리 출처 분리 및 인증이 함께 필요합니다.

TLS 구현 후 관리 출처에만 묶인 HttpOnly·Secure·SameSite 쿠키를 기본으로 사용합니다. HTTP 상태에서 Secure 쿠키만 켜거나 보안이 완성됐다고 표시하지 않습니다.

### 선택: 관리자 네트워크 허용 목록

- IPv4 및 IPv6 CIDR을 지원합니다. 사용자가 원하면 관리자 접근을 특정 네트워크로 제한합니다.
- HTTP 연결의 실제 peer address를 기준으로 검사하고 X-Forwarded-For를 신뢰하지 않습니다. IPv4-mapped IPv6도 같은 정책으로 처리합니다.
- 사설 IPv4 대역이라는 이유만으로 허용하지 않습니다. 라우팅 가능한 ULA·IPv6 역시 구성된 정책으로 판단합니다.
- IP 허용 목록을 신원 인증이나 암호화 대신 사용하지 않습니다. 변하는 휴대전화 단일 IP를 기본 등록 대상으로 삼지 않습니다.
- 적용 전에 현재 관리자가 차단되는지 확인하고, 임시 정책 적용 후 확인하지 않으면 이전 정책으로 복구합니다.

## 사용자 편의 및 복구

하드웨어 변경 없이 구현합니다.

- 일반 방문자는 제품의 .local 주소 또는 QR로 콘텐츠에 접근합니다. 관리자 승인 요구는 콘텐츠 조회에 적용하지 않습니다.
- 최초 설정은 보호된 설정 Wi-Fi와 짧은 등록 가능 시간으로 제한합니다. 가능하면 제품별 WPA2 암호를 QR로 제공하여 입력 부담을 줄입니다.
- 등록 중 만료·잘못된 입력·네트워크 이동을 사용자가 이해할 수 있는 문구로 표시합니다.
- 관리자 분실 시 별도 복구 코드로 관리자 등록을 재설정합니다. 기존 인증 코드를 읽거나 반환하지 않습니다.
- 복구 코드는 공장 MAC으로 계산하지 않고 무작위로 발급하며 재발급·사용 시 이전 코드를 폐기합니다.
- 물리 버튼/시리얼을 일반 사용자의 필수 복구 수단으로 삼지 않습니다. 모든 관리자와 복구 코드를 잃은 경우에는 판매자 지원 절차를 마련합니다.
- 웹 콘텐츠 초기화는 관리자 승인 후 파일과 첫 화면만 초기화하고, 소유권·화이트리스트·Wi-Fi 보안 설정을 보존합니다. 소유권 이전 초기화는 별도 기능입니다.

## API 허용 정책

| 기능 | 허용 대상 |
|---|---|
| 공개 웹페이지·미디어 | 일반 방문자; 서버 제한 적용 |
| 최초 Wi-Fi 설정·첫 관리자 등록 | 설정 단계의 등록 코드 소지자 |
| 관리자 로그인 | 화이트리스트에 등록된 브라우저 또는 승인된 등록 절차 |
| 시스템 상태·로그·파일 목록·상세 설정 | 유효한 관리자 세션 |
| 업로드·삭제·메인 지정·Wi-Fi 변경 | 유효한 관리자 세션 + 요청 위조 방어 |
| 화이트리스트 변경·복구 정보 변경·초기화 | 관리자 재인증 |
| OTA | 관리자 재인증 + 서명된 이미지 검증 |
| AI 파일 읽기 | 관리자가 명시적으로 허용한 범위 |
| AI 파일 쓰기·메인 변경 | 별도 제한 권한 + 사용자 승인 |

모든 API는 서버에서 기본 거부 정책을 사용합니다. 페이지에서 버튼만 숨기거나 로그인 팝업만 띄우는 방식은 보호로 인정하지 않습니다.

## 단계별 구현

### 1단계: API 보호 및 정보 유출 차단

1. 공통 인증/권한 검사 함수를 만들고 모든 관리자 API에 적용합니다.
2. 저장된 Wi-Fi 비밀번호를 HTML에 보내는 동작을 제거합니다.
3. 평문 관리자 비밀번호의 브라우저 저장을 제거하고, 세션 및 소금값을 포함한 비밀번호 검증값 저장으로 교체합니다.
4. 로그인 실패 제한, 전역 요청 제한, 요청 크기·수신 시간 제한을 추가합니다. IP당 제한만 두면 우회·서비스 거부가 가능하므로 함께 설계합니다.
5. Origin/Host 검사와 CSRF 방어를 추가하고 관리자 CORS는 기본 차단합니다. Host 검사는 제품명과 허용된 접근 주소를 정확히 비교합니다.
6. 보안 로그에 인증 성공/실패, 파일 변경, OTA, 복구를 기록하되 암호·토큰은 기록하지 않습니다.

### 2단계: 화이트리스트와 소유권 등록

1. 최초 등록, 관리자 브라우저 승인/취소, 장기 토큰과 만료 세션 구현.
2. 제품별 초기 비밀값 및 복구 코드 공급 방식 구현.
3. IP/CIDR 제한은 선택 기능으로 추가하고 자동 복구 적용 방식 도입.
4. 관리자 화면에 보안 탭 추가. 현재 브라우저, 승인 목록, 세션 종료, 복구 코드 관리 표시.

### 3단계: 웹 콘텐츠 및 AI 격리

1. 콘텐츠와 관리 UI의 웹 출처를 분리합니다. 같은 출처의 임의 HTML은 관리 인증 정보와 API에 접근할 수 있으므로 CSP만으로 해결하지 않습니다.
2. 관리 출처에는 제품이 제공한 UI만 올리고 임의 HTML 업로드를 금지합니다. 같은 IP의 포트만 다르게 쓰면 쿠키가 포트로 분리되지 않으므로 쿠키·Origin 정책도 별도로 설계합니다.
3. 파일 확장자·길이·이름·경로·예약 파일 목록을 검사하고 시스템 파일/설정/비밀 자료 접근을 금지합니다.
4. 업로드는 임시 파일로 저장·검사한 뒤 교체하고 실패 시 원본을 보존합니다.
5. AI에는 관리자 비밀번호 대신 제한된 작업 권한을 제공합니다. 읽기/쓰기/메인 변경을 나누고 범위·시간·횟수를 제한합니다.
6. AI가 읽은 HTML이나 모델 출력의 명령을 관리 권한으로 취급하지 않습니다. 원본 비교와 쓰기 승인 절차를 둡니다.

### 4단계: 전송 암호화 및 업데이트 보호

1. TLS 신뢰 모델을 확정합니다. 일반 공인 인증서는 .local 이름에 발급할 수 없으며 자체 서명 인증서는 브라우저 경고를 만들 수 있습니다. 판매용으로 회사 도메인·인증서 공급 또는 앱/중계 기반 보안 관리를 검토합니다. mDNS는 로컬 발견용으로 유지할 수 있습니다.
2. 설정 Wi-Fi 보호는 HTTP 암호화를 대체하지 않습니다. 자격증명·세션의 네트워크 탈취 위험이 남아 있음을 관리합니다.
3. 서명된 OTA, 타깃/버전 검사, 실패 시 롤백, 업데이트 중 전원 손실 처리.
4. Secure Boot·Flash Encryption·NVS Encryption을 생산용 설정으로 준비합니다. 키 보관·기기별 공급·서비스 복구 절차를 먼저 정하고 별도 시험 기기에서 검증합니다.
5. eFuse 및 다운로드/JTAG 제한은 되돌리기 어려울 수 있으므로 개발 보드에 자동 적용하지 않습니다.

## 검증 계획 — 아직 실행하지 않음

- 비로그인 직접 업로드·삭제·OTA·Wi-Fi 변경이 모두 거부되는지 확인.
- 등록되지 않은 브라우저·취소된 토큰·만료 세션의 거부 확인.
- 허용 네트워크 밖의 IPv4/IPv6 및 mapped 주소 거부 확인.
- 허용 목록 오설정 자동 복구와 관리자 분실 복구 확인.
- 업로드 HTML에서 관리 API/인증 자료에 접근하려는 시도 확인.
- CSRF·DNS rebinding·악성 Origin·경로 조작·큰 요청·인증 실패 폭주 확인.
- AI 도구 범위 이탈·동시 파일 수정·만료 권한 확인.
- S3/C3의 메모리 사용과 정상 사용자 접속·음원 스트리밍·mDNS 재연결 회귀 확인.
- OTA 서명 오류·전원 중단·롤백, TLS 인증서 및 시계 오류 흐름 확인.
