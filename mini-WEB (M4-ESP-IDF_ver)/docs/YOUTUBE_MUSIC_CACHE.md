# 유튜브 뮤직 캐시·다운로드·다음 곡

현재 곡과 목록의 다음 곡을 부팅 동안 유지하는 두 PSRAM 슬롯에 자동 적재한다.
PC 중계서버가 음원을 MP3 64 kbit/s, 32 kHz, 스테레오로 변환한다. 보드가
다시 재생하거나 탐색할 때는 보관한 압축 데이터를 디코딩하므로 HTTP로
PCM을 다시 요청하지 않는다. 적재 완료한 곡은 Wi-Fi가 끊겨도 재생할 수 있다.
처음 선택한 곡은 PC 준비와 보드 적재를 기다린다. 이미 준비된 다음 곡은
기존 슬롯을 그대로 사용한다. 새 검색은 현재 재생 목록을 바꾸지 않는다.

`다음 곡 이어서`가 켜져 있으면 정상 종료 후 **오디오 작업이 직접 다음 곡을
예약**한다. UI의 재생 종료 순간 감지에 의존하지 않는다. 사용자의 정지·다른
오디오 작업·기존 대기 요청을 보존한다. UI는 새 곡을 감지하면 제목·커버와
그다음 곡의 사전 적재를 갱신한다. 목록 마지막에서는 멈춘다. 실패·중단·
누락된 END 패킷·디코더 오류를 정상 종료로 취급하지 않는다.

## SD 저장

현재 곡의 `SD카드에 저장`, `다음 곡 저장` 버튼을 제공한다. 저장 중에는
진행률과 취소 버튼을 표시한다. 경로는 SD 루트의 **`media/YouTube Music`**,
파일명은 `제목_유튜브ID.mp3`다. 일반 음악 앱에서 찾아 재생할 수 있다.
PSRAM에 준비된 곡은 네트워크 재다운로드 없이 저장한다. 공간 부족 또는
캐시 한도 초과로 PSRAM에 둘 수 없는 곡도 PC에서 SD로 직접 전송한다.
완성 파일은 덮어쓰지 않는다. `.part`에 기록·동기화한 뒤 이름을 변경하고,
취소·쓰기 오류·불완전 수신이면 임시 파일을 제거한다.

## 제한과 소유권

- PSRAM은 곡당 최대 8 MiB, 두 곡 합계 최대 16 MiB다. 추가 할당 전 4 MiB
  여유를 남긴다. 실제 할당 실패도 확인하며 재부팅으로 복구하지 않는다.
- 64 kbit/s에서 5분 곡의 압축 데이터는 약 2.4 MB다. 기존 32 kHz 모노
  PCM 전송의 64 KB/s에 비해 압축 파일은 약 8 KB/s다. 이는 형식상 계산이며
  실기 전송 속도·지연 개선 측정값은 아니다.
- PC의 곡 길이 제한은 20분, 출력은 최대 10 MiB다. PSRAM 한도를 넘거나
  메모리가 부족하면 기존 PCM 스트리밍 재생을 사용한다. 저장은 SD로 직접 가능하다.
- 캐시 작업 하나가 HTTP와 SD 쓰기를 담당한다. 내부 스택은 10 KiB이며
  제어·잠금은 내부 RAM, MP3·디코더 출력 32 KiB는 PSRAM을 사용한다.
- 재생/저장이 참조한 완성 버퍼는 참조가 끝날 때까지 해제하지 않는다.
  슬롯은 현재 곡·다음 곡·대기 중인 SD 저장을 고려해 교체한다.
- SD 다운로드는 영상 다운로드와 하나의 작업 상태를 공유하며 동시 저장을 막는다.
  현재 곡의 PSRAM 재생과 다음 곡 준비는 병행한다. 재부팅하면 PSRAM 캐시는 사라진다.

## PC 변경과 실패 표시

기존 로그에는 오디오 구간 다운로드 실패와 upstream 403이 있었다. 음악은
직접 URL의 수동 구간 다운로드 대신 yt-dlp의 다운로드 경로를 사용한다.
첫 오디오 형식이 실패하면 `ba/b` 선택으로 한 번 더 시도한다. 원본 컨테이너가
달라도 동일한 MP3를 전달한다. 삭제·지역 제한·인증이 필요한 곡의 재생을
보장하지는 않는다. 재생 가능한 특정 곡의 실물 확인은 별도로 필요하다.

서버 API는 기존 토큰 인증을 유지한다. `POST /api/music`,
`GET /api/music/status?job=...`, `GET /api/music/file?job=...`을 추가했다.
status의 DELETE는 준비 작업을 취소한다. `/api/status`의 `music_cache: 1`로
지원 여부를 확인한다. MP3 파일과 메타데이터는 PC `cache/music`에 보관한다.
PC 준비 작업은 최대 2개, 완료 캐시는 최대 64곡/256 MiB로 제한한다.
기존 `/api/play?audio=1`도 이 압축 캐시를 PCM으로 변환해 제공한다.

음원 추출 옵션은 [yt-dlp 공식 문서](https://github.com/yt-dlp/yt-dlp#download-options)를
확인했고, 실제 설치된 ESP-IDF 5.5.5 및 오디오 코덱 헤더와 선언을 대조했다.

## 새로고침 표시

사진·갤러리·음악의 새로고침 설명은 각각 `PHOTO_REFRESH`, `GALLERY_REFRESH`,
`MUSIC_REFRESH` 번역 키로 분리했다. 버튼에는 공통 새로고침 아이콘만 보인다.
각 버튼의 user_data에 해당 설명 ID를 보관하며 실행 콜백은 기존 앱별로 유지한다.
Wi-Fi 검색·게임 재시작·설정 적용은 서로 다른 동작이므로 기존 이름을 유지한다.

## 검증과 적용

`node tools/test_tube_music_cache.cjs`는 실제 C 본문의 적재·슬롯 교체·참조 보호,
디코딩/탐색·종료·취소·SD 저장·저메모리 스트리밍 복구를 호스트 모의 객체로 검사한다.
`test_ytmusic.cjs`는 작업에서 전환된 곡을 UI가 중복 제출 없이 반영하는지 검사한다.
PC `node test_media.mjs`는 합성 음원, 실제 FFmpeg/ffprobe와 로컬 HTTP로 MP3
출력·다운로드·대체 형식 재시도·실패와 정상 종료 구분을 검사한다.
펌웨어 컴파일·새 네이티브 UI 렌더링·보드의 실제 디코더/SD/장시간 재생은 미확인이다.
시뮬레이터 시나리오 110~112에 캐시 준비·완료·SD 저장 상태를 추가했다.

PC 중계서버를 새 파일로 재시작하고, M4 폴더에서 사용자가 빌드·플래시한다.

```powershell
.\m4.ps1 -Action Build
.\m4.ps1 -Action Flash -Port COM8
```

`COM8`은 실제 보드 포트로 바꾼다. 실기에서는 다음 곡 자동 전환, 한 곡만 모드,
캐시 후 오프라인 재생, 탐색·빠른 곡 변경·저장 취소·SD 오류·다른 앱 전환과
최소 힙/스택 여유를 확인한다. PC 서버 변경만으로 기존 펌웨어에 버튼이 생기지는 않는다.
